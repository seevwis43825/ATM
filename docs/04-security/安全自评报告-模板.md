## 一、安全设计总则

本系统面向金融业务场景，遵循"**最小权限、默认拦截、全程留痕、人工兜底**"四项原则：

| 原则 | 落地方式 |
|---|---|
| 最小权限 | Agent 只能调用已注册的工具，无法执行任意代码或访问未授权数据 |
| 默认拦截 | 所有涉及资金变动的操作默认进入待确认状态，必须用户显式授权 |
| 全程留痕 | 关键操作写 HMAC 链 JSONL 与独立 `audit_events`；写失败记 Critical，但当前不阻断业务 |
| 人工兜底 | 高风险操作强制人工确认，模型无法自行绕过 |

## 二、权限分级实现说明（平台明确要求）

### 2.1 三级风险分级

| 等级 | 判定依据 | 代表操作 | 处理方式 |
|---|---|---|---|
| **低风险** | 仅读取数据，不产生资金变动 | 查询余额、账单分析、产品浏览 | 直接执行，仅记日志 |
| **中风险** | 产生资金变动但金额小、可逆 | 小额转账（<1000）、卡片解锁、订阅取消 | 生成确认卡片，用户点击确认后执行 |
| **高风险** | 大额资金变动、不可逆、影响账户安全 | 大额转账（≥5000）、理财申购赎回、卡片挂失、额度调整 | 二次确认 + 明确风险提示 + 强制记录审计日志 |

### 2.2 当前代码实现

当前实现为 C#/.NET 插件架构，不是 TypeScript `apps/api`。请求身份从 JWT 提取；转账插件在副作用提交前返回 `RequiresHumanInLoop`，确认接口再携带 `confirmed` 槽位继续执行。示意：

```csharp
var result = await router.RouteAsync(request, ct);
// 未确认时返回 RequiresHumanInLoop=true、SideEffectCommitted=false；
// /api/chat/confirm 校验令牌身份后，以 confirmed=true 继续执行。
```

当前处理规则：
1. 资金操作未确认时不提交副作用，返回人工回环状态
2. 确认接口再次校验 JWT 身份，不能由请求体切换普通用户身份
3. 确认动作写审计；拒绝流程及所有风险等级展示仍需逐场景测试举证

### 2.3 权限分级矩阵

| 角色 | 转账 | 账单 | 理财 | 卡片 | 审计日志 |
|---|---|---|---|---|---|
| 普通用户 | 需确认 | 可查 | 需确认 | 需确认 | 仅本人 |
| 管理员 | 需确认 | 可查 | 需确认 | 需确认 | 具备审计角色能力时可查 |
| Agent（系统） | 未确认不提交；确认后由服务端执行 | 可查 | 依插件实现 | 依插件实现 | 写入审计 |

> **边界**：当前保护点是“未确认不提交 + 服务端身份绑定”，不能表述成 Agent 永远没有执行能力。确认后仍由后端 Agent/插件执行，因此还需 MFA、交易签名、限额和真实银行侧风控。

## 三、已知风险清单（平台明确要求）

| # | 风险项 | 等级 | 场景描述 | 缓解措施 | 残留风险 |
|---|---|---|---|---|---|
| R1 | 提示词注入 | 高 | 用户在对话中嵌入恶意指令，诱导 Agent 越权操作 | 输入长度限制、敏感指令模式过滤、工具白名单 | 中：复杂变体仍可能绕过 |
| R2 | 误操作转账 | 中 | 用户口误或 Agent 理解偏差，转错人/错金额 | 强制确认卡片 + 收款人信息完整展示 + 金额二次核对 | 低 |
| R3 | 模型幻觉 | 中 | Agent 编造不存在的交易记录或产品信息 | 所有数据必须来自工具返回，禁止模型自行生成数值 | 低 |
| R4 | 敏感信息泄露 | 高 | 对话、SQLite 或日志暴露卡号/身份数据 | 展示脱敏；`TransferRecord` 敏感字段加密 | 中：无 TDE/KMS，覆盖需盘点 |
| R5 | 无授权调用 | 中 | 未登录用户调用接口 | 会话鉴权、sessionId 校验、接口限流 | 低 |
| R6 | 审计日志篡改/丢失 | 高 | 攻击者修改记录或单路写入失败 | HMAC 链 JSONL + `audit_events` 双写 | 中：无 WORM；失败不阻断业务 |
| R7 | 数据越权访问 | 中 | 用户 A 查询用户 B 的账单 | 所有查询强制带 `userId` 条件，服务端校验归属 | 低 |
| R8 | 依赖库漏洞 | 中 | NuGet 第三方包存在已知 CVE | 版本评审；规划 NuGet/OSV 扫描、SBOM 与锁文件 | 中 |
| R9 | 密钥/API Key 泄露 | 高 | 配置或仓库中出现密钥 | 配置留空、环境变量注入、安全门校验 | 中：无 KMS/Vault，CI 无完整密钥扫描门禁 |
| R10 | 对话上下文污染 | 低 | 长对话导致 Agent 遗忘安全规则 | 系统提示词固化、每轮重注入安全约束 | 低 |

## 五、已知不足与改进方向

诚实说明局限，比假装完美更可信：

1. **Mock 数据局限**：当前使用模拟数据，未接入真实银行核心系统，生产环境需补充交易冲正、对账等机制
2. **异常识别规则化**：目前依赖规则而非模型，对新型欺诈模式识别能力有限
3. **无多因素认证**：缺少短信验证码、生物识别等强验证手段
4. **审计归档未生产化**：已有 HMAC 链签名与数据库双写，但无 WORM/可信时间戳；写失败仅告警
5. **生产数据控制未完成**：无 KMS/Vault、TDE、RLS，默认 SQLite + `EnsureCreated`
6. **安全门禁不完整**：CI 有 EF migration gate，但无完整 SAST/DAST、镜像、依赖与密钥扫描阻断链

## 六、结论

本系统已实现基础权限、人工确认、字段加密与可验证审计链，但尚未形成生产安全闭环。当前主要残留风险包括 MFA、生产密钥托管、传输与数据库加密、不可变归档、生产监控以及完整安全扫描门禁。

**自评结论：适合作为演示/研发基线；在 Target 控制完成并取得部署、测试与合规证据前，不应宣称符合生产金融安全要求。**
