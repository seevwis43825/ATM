## 一、安全设计总则

本系统面向金融业务场景，遵循"**最小权限、默认拦截、全程留痕、人工兜底**"四项原则：

| 原则 | 落地方式 |
|---|---|
| 最小权限 | Agent 只能调用已注册的工具，无法执行任意代码或访问未授权数据 |
| 默认拦截 | 所有涉及资金变动的操作默认进入待确认状态，必须用户显式授权 |
| 全程留痕 | 每次工具调用生成唯一 `auditId`，记录操作人、时间、参数、结果 |
| 人工兜底 | 高风险操作强制人工确认，模型无法自行绕过 |

## 二、权限分级实现说明（平台明确要求）

### 2.1 三级风险分级

| 等级 | 判定依据 | 代表操作 | 处理方式 |
|---|---|---|---|
| **低风险** | 仅读取数据，不产生资金变动 | 查询余额、账单分析、产品浏览 | 直接执行，仅记日志 |
| **中风险** | 产生资金变动但金额小、可逆 | 小额转账（<1000）、卡片解锁、订阅取消 | 生成确认卡片，用户点击确认后执行 |
| **高风险** | 大额资金变动、不可逆、影响账户安全 | 大额转账（≥5000）、理财申购赎回、卡片挂失、额度调整 | 二次确认 + 明确风险提示 + 强制记录审计日志 |

### 2.2 代码实现

风险等级在工具函数返回时由 `riskLevel` 字段声明：

```ts
// apps/api/src/tools/transfer.ts
const riskLevel: RiskLevel = amount >= 5000 ? 'high'
  : amount >= 1000 ? 'mid' : 'low';

return {
  ok: true,
  code: 'OK',
  message: '...',
  needConfirm: true,     // 强制二次确认
  riskLevel,             // 风险分级
  auditId,               // 审计留痕
  data: { ... },
};
```

Agent 大脑层的处理规则：
1. `needConfirm === true` → **绝不直接执行**，必须转成确认卡片返回前端
2. `riskLevel === 'high'` → 在确认卡片上附加风险提示文案
3. 用户拒绝 → 操作中止并记录 `action: reject` 日志

### 2.3 权限分级矩阵

| 角色 | 转账 | 账单 | 理财 | 卡片 | 审计日志 |
|---|---|---|---|---|---|
| 普通用户 | 需确认 | 可查 | 需确认 | 需确认 | 仅本人 |
| 管理员 | 需确认 | 可查 | 需确认 | 需确认 | 全部可查 |
| Agent（系统） | 仅发起，无执行权 | 可查 | 仅发起，无执行权 | 仅发起，无执行权 | 只写不读 |

> **关键设计**：Agent 本身不具备执行权，只有"发起权"。真正的执行发生在用户确认之后。这样即使模型被诱导，也无法造成实际损失。

## 三、已知风险清单（平台明确要求）

| # | 风险项 | 等级 | 场景描述 | 缓解措施 | 残留风险 |
|---|---|---|---|---|---|
| R1 | 提示词注入 | 高 | 用户在对话中嵌入恶意指令，诱导 Agent 越权操作 | 输入长度限制、敏感指令模式过滤、工具白名单 | 中：复杂变体仍可能绕过 |
| R2 | 误操作转账 | 中 | 用户口误或 Agent 理解偏差，转错人/错金额 | 强制确认卡片 + 收款人信息完整展示 + 金额二次核对 | 低 |
| R3 | 模型幻觉 | 中 | Agent 编造不存在的交易记录或产品信息 | 所有数据必须来自工具返回，禁止模型自行生成数值 | 低 |
| R4 | 敏感信息泄露 | 高 | 对话中暴露完整卡号、身份证号 | 展示层统一脱敏（`6222 **** 8888`）、日志加密存储 | 低 |
| R5 | 无授权调用 | 中 | 未登录用户调用接口 | 会话鉴权、sessionId 校验、接口限流 | 低 |
| R6 | 审计日志篡改 | 低 | 攻击者修改操作记录掩盖痕迹 | 日志只写不改、append-only 存储 | 低 |
| R7 | 数据越权访问 | 中 | 用户 A 查询用户 B 的账单 | 所有查询强制带 `userId` 条件，服务端校验归属 | 低 |
| R8 | 依赖库漏洞 | 中 | 第三方包存在已知 CVE | 锁定版本、上线前跑 `npm audit` | 中 |
| R9 | API Key 泄露 | 高 | 前端代码或仓库中硬编码密钥 | `.env` 不入库、`.gitignore` 配置、上线前全仓库扫描 | 低 |
| R10 | 对话上下文污染 | 低 | 长对话导致 Agent 遗忘安全规则 | 系统提示词固化、每轮重注入安全约束 | 低 |

## 五、已知不足与改进方向

诚实说明局限，比假装完美更可信：

1. **Mock 数据局限**：当前使用模拟数据，未接入真实银行核心系统，生产环境需补充交易冲正、对账等机制
2. **异常识别规则化**：目前依赖规则而非模型，对新型欺诈模式识别能力有限
3. **无多因素认证**：缺少短信验证码、生物识别等强验证手段
4. **审计日志未做防篡改签名**：生产环境应引入区块链或可信时间戳

## 六、结论

本系统在架构层面实现了权限分级、强制确认、全程留痕的安全闭环，Agent 不具备直接执行资金操作的权限。当前主要残留风险集中在提示词注入与依赖安全，已在风险清单中列明并规划了改进方向。

**自评等级：符合金融场景基础安全要求，具备进一步加固能力。**
