### 需要补齐的 ADR（新发现）

以下决策在实现过程中产生，未写入原 ADR 文件：

| 新增 | 决策 | 原因 |
|------|------|------|
| **ADR-011** | 自研 `SimpleDbContextFactory` 替代 EF 内置工厂 | EF 的 `DbContextFactory<T>` 要求 DbContext 只有一个接受 `DbContextOptions` 的构造函数，而本项目需注入插件贡献器集合、当前用户、时钟 |
| **ADR-012** | 插件上下文用 `PluginContributorRegistry` 静态注册表 | 桥接工厂创建路径的依赖回填，避免工厂无法注入集合的问题 |
| **ADR-013** | `SlotReader` 统一处理 `JsonElement` 槽位 | JSON 反序列化后槽位是 `JsonElement`，直接强转失败。集中处理避免每个插件重复实现 |
| **ADR-014** | `AgentRouter` 最长前缀优先路由 | 避免 `transfer` 抢占 `transfer.receive` 的路由 |

### 压测暴露并修复的缺陷

| 缺陷 | 严重度 | 根因 | 修复 |
|------|-------|------|------|
| 审计链并发竞态 | **P0** | `Sign()` 在锁内读链尾，但 `_lastSignature` 赋值在锁外，多条记录会引用同一前序签名，**审计链断裂** | 抽出 `SignAndAdvance()`，读/算/写链尾合并到同一临界区 |
| 审计文件行撕裂 | **P1** | `File.AppendAllTextAsync` 并发调用会交错 | 加 `SemaphoreSlim(1,1)` 串行化文件写入 |
| 事件计数丢失 | P2 | `PublishedCount++` 裸自增 | 改 `Interlocked.Increment` |

> 当前测试是**演示级验证**，证明架构能跑通。生产前需补齐单元测试（覆盖率目标 ≥ 80%，见 [`../03-development/04-testing-strategy.md`](../03-development/04-testing-strategy.md)）与安全测试（见 [`../05-security-compliance/01-threat-model.md`](../05-security-compliance/01-threat-model.md) §7）。

## 9. 多人协同的工程保障（诚实评估）

### 9.1 已有

| 机制 | 状态 | 说明 |
|------|------|------|
| 模块边界 | ✅ | 每插件独立程序集，编译期隔离，跨插件引用会编译失败 |
| 契约稳定性 | ✅ | SDK 是唯一依赖面，改 SDK 需同步改所有插件（编译期暴露） |
| 文档分工 | ✅ | 5 份 by-role 分册 + 文档所有权矩阵 |
| 协同流程文档 | ✅ | 迭代作战地图、PR Review 清单、发布流程 |
| FeatureFlag 声明 | 🟡 | 插件 Manifest 声明开关名，但运行时未强制 |

### 9.2 缺失（影响多人并行开发）

| 缺失项 | 后果 | 优先级 |
|--------|------|--------|
| **无 CI 配置** | 合并前无自动验证，靠人工 | **P0** |
| **无单元测试** | 重构无安全网，改一个模块不知道会不会弄坏另一个 | **P0** |
| **代码未提交 git** | 全部是 untracked，无法回滚、无法协作、无法 code review | **P0** |
| **无 CODEOWNERS** | 改 Base 不会被自动通知架构师 | P1 |
| **无契约测试** | SDK 契约变更可能悄悄破坏插件兼容性 | P1 |
| **无覆盖率门禁** | 代码质量靠自觉 | P1 |
| **无并发回归** | 并发缺陷无法在 CI 中被发现 | P1 |

> **当前状态不适合 5 人同时开发**。单人演示可以，5 人并行会有三个直接风险：
> 1. 改坏别人模块但没人发现（无 CI + 无测试）
> 2. 无法回滚（代码未入库）
> 3. 改框架层不知道会破坏哪个插件（无契约测试）

### 9.3 5 人并行前的最小准备

按优先级，**半天内可完成**：

1. `git add` + 首次提交（10 分钟）
2. GitHub Actions：build + E2ETest + StressTest（2 小时）
3. 抽 3-5 个关键单元测试：合规规则、脱敏、幂等（半天）
4. `.github/CODEOWNERS`：Base → 架构师，plugins/* → 业务开发（10 分钟）

**做完这四项，5 人并行开发才有基本的安全网。**

## 10. 总结

| 维度 | 评估 |
|------|------|
| **架构骨架** | ✅ 完整可用，插件化、数据库管理、安全合规三块基础设施到位 |
| **可运行性** | ✅ 端到端 30/30 + 压力 29/29 通过，真实扣款、幂等、合规拦截、并发一致性均实测 |
| **并发正确性** | ✅ 已实测（200 并发审计链、20 并发转账、30 并发对话），并修复 3 处竞态 |
| **演示价值** | ✅ 足以支撑答辩、评审、方案汇报 |
| **5 人并行开发** | ❌ 缺 CI、缺单测、代码未入库，**不具备协作前提** |
| **生产就绪度** | ❌ 差距明显：鉴权、加密、迁移、规则覆盖均需补齐 |
| **多 Agent 深度** | 🟡 插件化多 Agent 架构已立，协作式编排与记忆未做 |

**结论**：本代码是**架构原型 + 可运行基座**，并发正确性经实测验证，证明了「多 Agent 插件化 + 强合规约束」的技术路线可行。

**但它目前不适合 5 人同时开发**（见 §9.2），也不适合生产上线（见 §8 的 P0 八项）。下一步优先级应是 §9.3 的协作安全网，而非继续加功能。
