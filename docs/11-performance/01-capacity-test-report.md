## 1. 本轮改了什么

本轮性能工作共 4 处代码改动 + 2 处缺陷修复，每处都对应一个可解释的机制。

### 1.1 审计库改「入队 + 后台批量提交」

**问题**：审计写入在**请求关键路径**上，而旧实现每条审计事件都单独提交一次 SQLite 事务（含 fsync）。这笔成本被完整摊在每个请求上。

**改法**：`AuditDbWriter`（`BackgroundService`）用有界 `Channel` 接收审计事件，攒批（默认 200 条）后一次事务提交；读路径在返回前先 `FlushAsync`，保证"写完立刻查"查得到；停机时 drain，不留审计尾巴。

**关键取舍**：
- **权威记录仍然是同步的** —— HMAC 链式签名 + JSONL 归档在请求返回前就已落盘；
- **数据库只是可检索副本** —— 《反洗钱法》第 30 条要求交易记录"可供查验"，载体是 JSONL + 链签名（可离线校验完整性），数据库提供按操作者/时间/场景检索的能力；
- **队列有界、满了背压等待，绝不丢审计记录**；
- **崩溃时最多丢「尚未批量提交」的数据库副本尾部**，JSONL 与签名链完好无损 —— 审计的**可篡改性**由链式签名保证，不依赖数据库副本；
- **除崩溃外，批量提交失败同样只记 `Critical`**（`AuditDbWriter.CommitCoreAsync` 捕获异常后不重试、不补偿），该批**数据库副本直接丢失**；JSONL 权威记录仍在。生产需补可靠队列 + 对账 + 告警闭环（见 §7 未覆盖项）。

### 1.2 审计库与业务库切 SQLite WAL

- `PRAGMA journal_mode=WAL`（读写不互斥）：**库文件的持久属性**，启动时设一次即长期生效；
- `PRAGMA synchronous=NORMAL`（提交免 fsync）：**连接级设置，不是文件属性**。当前只在初始化时的那条连接上执行（`DatabaseInitializer.EnableSqliteWriteAheadLogAsync`），写路径的连接由 `IDbContextFactory` 另建，**是否继承取决于连接池是否复用同一条物理连接**（实测复用时会继承，但不保证）。

  ⇒ **"提交不必 fsync" 只能算 best-effort，不能作为稳定结论。** 真正的兜底是批量提交本身 —— 提交次数已被摊薄到原来的 1/200。

  > 2026-10-20 复核更正：早期版本把这两个 pragma 一并说成"库文件持久属性"，是错的。

### 1.3 跨行聚合读路径改走内存快照

跨行卡片查询要同时问 3 家银行。改造前每次请求要开 3 个库、建 3 次连接、发 3 条 SQL，实测比内存字典慢约 5 倍。
现在 `BankLedger` 在启动时把本行数据载入内存快照，读路径走内存，**SQLite 仍是持久化的真相来源**（写路径落库后同步更新快照）。
代价：同一库被多个进程打开时快照不共享（Mock Bank 正常单实例运行，不受影响）。

### 1.4 HttpClient 日志降到 Warning

`System.Net.Http.HttpClient` 在 Information 级别下会为**每个 HTTP 请求**打印起止两行。这两行没有任何诊断价值（真正的耗时在 `ElapsedMs` 里），却让每个请求多两次格式化 + 两次控制台写。已按 Microsoft 官方默认做法在 `appsettings.json` 中降级为 `Warning`。

### 1.5 顺带修掉的两个真实缺陷

| 缺陷 | 严重度 | 根因 | 修复 |
|------|-------|------|------|
| **MockBank 重启必崩** | **P0** | 「库里是否为空」的种子守卫改读了**内存快照**，而守卫发生在快照载入**之前** → 永远判空 → 每次启动都重播种子 → 撞 `accounts.AccountNo` 唯一约束，服务起不来 | 守卫改查数据库（`CountAll` 走 EF 计数） |
| **会话记忆并发下 500** | **P0** | 淘汰逻辑用 LINQ `OrderBy` 直接排序 `ConcurrentDictionary`，走的是 `ICollection.CopyTo` 批量拷贝路径 —— 该路径在字典被并发修改时抛 `ArgumentException`，随后半填的数组产生 null key，后续 `TryRemove` 再抛 `ArgumentNullException` | 改用枚举器取快照再排序；并新增 5 项测试（其中 **2 项为并发回归用例**，旧实现下确实失败、修复后通过；另 3 项为行为护栏） |

> 这两个缺陷在低并发下完全看不出来（单元测试、E2E 串行脚本都测不到），
> 是在真实并发压测下才暴露的 —— 第 2 个缺陷在 5 并发下即可复现 HTTP 500
> （某次观察到的失败比例为 12.5%；**原始压测日志未随仓库保留**，故此处只给定性结论）。

## 3. 决定性证据：进程内 A/B

### 3.1 为什么必须做进程内 A/B

端到端 QPS 受机器负载、磁盘缓存、后台进程、杀毒软件扫描共同影响，噪声可达 2 倍。
要把"改了什么"和"机器在忙"分开，必须在**同一进程内**、**紧挨着**量同一件事。

### 3.2 审计落库：逐条提交 vs 批量提交

`src/StressTest` 新增「测试 7」，在同一个临时 SQLite 库上分别用两种方式写入 300 条审计事件。

| 轮次 | 来源 | 逐条 300 次提交 | 批量 300 条一次提交 | 加速比 |
|------|------|-----------------|---------------------|--------|
| 1 | 本轮 | 1,865.6ms（161 条/秒） | 72.7ms（4,129 条/秒） | **25.7×** |
| 2 | 本轮 | 2,106.3ms（142 条/秒） | 100.4ms（2,989 条/秒） | **21.0×** |
| 3 | 本轮 | 1,288.7ms（233 条/秒） | 72.7ms（4,129 条/秒） | **17.7×** |
| 4 | 复核 agent | 838.5ms（358 条/秒） | 49.2ms（6,092 条/秒） | **17.0×** |
| 5 | 复核 agent | 1,161.7ms（258 条/秒） | 63.8ms（4,704 条/秒） | **18.2×** |
| 6 | 复核 agent | 1,141.8ms（263 条/秒） | 52.5ms（5,709 条/秒） | **21.7×** |
| 7 | 复核 agent | 1,315.8ms（228 条/秒） | 63.3ms（4,739 条/秒） | **20.8×** |

**7 次实测的结论：加速比 17.0~25.7×（离散 1.51×），逐条 142~358 条/秒、批量 2,989~6,092 条/秒。**

**这个 17~26 倍量级就是审计批量化的全部价值来源**：
旧实现每个请求要付的正是"逐条"那一列的成本；新实现把它摊到批上。
端到端 QPS 之所以只提升 3~6 倍而不是 20 倍，是因为端到端还包含鉴权、意图识别、Agent 编排、
HTTP 往返、脱敏序列化等**与本次优化无关的固定成本**。

> ⚠️ **进程内 A/B 本身也有离散度**（约 1.5 倍），结论要看区间不要看单点。
> 绝对速率（142~358 / 2,989~6,092 条每秒）是**本机**的量级，在别的机器上不复现。

复现命令：

```powershell
dotnet run --project src/StressTest -c Release -- http://localhost:5243 http://localhost:5200
```

## 4. 测量可靠性（必读）

### 4.1 本机端到端数字不可复现

同一构建、同一套工具、同一天内，对**完全相同**的端点复测：

| 被测对象 | 第 1 次 | 第 2 次 | 离散度 |
|---------|--------|--------|--------|
| `/api/chat` 5 并发 QPS | 290.0 | 142.8 | **2.0×** |
| `/api/chat` 20 并发 QPS | 91.7 | 198.0 | 2.2× |
| `/health` 定点测速 | 1,211 req/s | 282 req/s | **4.3×** |

`/health` 是本项目最简单的端点（无数据库、无审计、无下游调用），它的 4.3 倍离散度说明
**波动来自机器而非应用**。因此：

- ✅ 可以用：进程内 A/B（§3.2，**但它本身也有约 1.5 倍离散，须看区间不要看单点**）、错误率、是否有 5xx、超时数；
- ❌ 不要用：单次端到端 QPS 作为容量结论或 SLA 依据。

### 4.2 复现步骤（必须按顺序）

```powershell
# 1. 先关限流，否则 99% 会被 429 挡掉
$env:RateLimit__Enabled="false"
$env:CoreBank__BaseUrl="http://localhost:5200"

# 2. 起 MockBank（故障注入只在 Development 或 MockBank__EnableFaultInjection=true 下开启）
$env:ASPNETCORE_ENVIRONMENT="Development"
dotnet run --project src/mock-bank/MockBank.Api -c Release -- --urls http://localhost:5200

# 3. 起宿主
dotnet run --project src/src/BankingAgent.Host -c Release -- --urls http://localhost:5243

# 4. 压测（约 2.5 分钟）
dotnet run --project src/LoadTest -c Release -- http://localhost:5243 http://localhost:5200
```

> **三个环境陷阱**（本轮都踩过）：
> 1. `dotnet run` 会自动套用 `Properties/launchSettings.json`（含 `ASPNETCORE_ENVIRONMENT=Development` 与开发密钥），
>    **直接跑 DLL 不会** —— 直接 `dotnet <dll>` 启动会因缺 `Crypto:DataEncryptionKey` 而启动失败，
>    故障注入也会因环境不是 Development 而被静默忽略（返回 200 而不是 503）。
> 2. Windows 命令行传参会**吃掉 JSON 里的双引号**：把 `{"a":"b"}` 传给子进程会变成 `{a:b}`，
>    服务端直接回 400。`scripts/bench-endpoint.ps1` 因此提供 `-BodyFile` 读 UTF-8 文件传请求体。
> 3. **E2E 场景 5 会从演示账户转出 30,000 元**，跑之前必须重置 MockBank 库
>    （`POST http://localhost:5200/api/corebank/v1/_admin/reset`，或删除 `App_Data/*.db*`），
>    否则余额被前几轮压测耗尽，E2E 会以 `INSUFFICIENT_FUNDS` 失败（实测 63/70、67/70）。

## 5. 瓶颈清单（更新）

| # | 瓶颈 | 当前状态 | 生产要求 | 优先级 |
|---|------|---------|---------|--------|
| 1 | **审计逐条落库** | ✅ 已改批量异步提交（进程内实测 17.0~25.7 倍） | 换 PostgreSQL 后仍建议批量 | **已解决** |
| 2 | **SQLite 单文件写锁** | ✅ 已切 WAL + 批量提交 | PostgreSQL，读写分离 | P0 |

| 8 | **无熔断降级** | 下游挂了会拖垮 | Polly 熔断 + 降级 | **P0** |

| 11 | **审计批量提交失败无补偿** | ⚠️ 只记 `Critical`，该批数据库副本丢失且不重试 | 可靠队列 + 对账 + 告警闭环 | **P0** |

> 第 7 项说明：曾尝试把审计文件改为**长连接句柄**（省掉每条 open+close），
> 但常驻写句柄会让用标准 `File.ReadAllLines`（`FileShare.Read`）读取审计文件的外部工具**直接打不开**——
> 审计日志必须能被合规工具读取，1% 的 CPU 收益不值得这个代价，**已撤回该改动**。

## 6. 容量换算（仅示例，非承诺）

| 指标 | 值 |
|------|-----|
| 峰值吞吐 | 198 QPS |
| 安全运行水位（峰值 198 QPS × 60%） | 119 QPS |
| **安全水位**日处理能力（= 峰值 × 60% × 86400） | 10,264,320 请求/天 |
| **峰值**日处理能力（= 198 × 86400） | 17,107,200 请求/天 |
| 峰值日处理（15% 峰值系数） | 1,539,648 请求/天 |

**银行场景估算**（假设 10 万日活用户、人均 10 次对话/日、峰值系数 4）：

```
日请求量 = 100,000 × 10 = 1,000,000
峰值 QPS = 1,000,000 / 86,400 × 4 ≈ 46 QPS
```

> **示例判断（非容量承诺）**：在所有假设成立时，本报告的水位覆盖示例中的 46 QPS；
> 生产副本数必须经目标环境压测、冗余要求和故障场景重新计算。

## 8. 与历史报告的关系

- **历史基线 296 QPS @ 200 并发（P99 812ms，2026-09-28）** 来自**优化前**的架构：
  审计逐条落库、Mock Bank 单库 + 全局转账锁。旧报告把瓶颈归因为「Mock Bank 的全局锁」，
  该归因**已随多银行拆分失效**（转账锁现在是按行、按账户号的字典序锁）。
- 本报告的 198 QPS 峰值与历史的 296 QPS **不构成直接可比**（架构不同、机器状态不同、噪声量级不同）。
- 真正可比的只有 §3.2 的进程内 A/B，以及 §1.5 的缺陷清单。
