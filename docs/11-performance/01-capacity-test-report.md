## 1. 本轮改了什么

### 1.1 审计库改「入队 + 后台批量提交」

**问题**：审计写入在**请求关键路径**上，而旧实现每条审计事件都单独提交一次 SQLite 事务（含 fsync）。

**改法**：`AuditDbWriter`（`BackgroundService`）用有界 `Channel` 接收审计事件，攒批（默认 200 条）后一次事务提交；读路径在返回前先 `FlushAsync`，保证"写完立刻查"查得到；停机时 drain。

**关键取舍**：
- **权威记录仍然是同步的** —— HMAC 链式签名 + JSONL 归档在请求返回前就已落盘；
- **数据库只是可检索副本** —— 《反洗钱法》第 30 条要求交易记录"可供查验"，载体是 JSONL + 链签名，数据库提供按操作者/时间/场景检索的能力；
- **队列有界、满了背压等待，绝不丢审计记录**；
- **崩溃时最多丢「尚未批量提交」的数据库副本尾部**，JSONL 与签名链完好 —— 审计的**可篡改性**由链式签名保证，不依赖数据库副本；
- **除崩溃外，批量提交失败会先有界重试**（含首次共 3 次尝试，即最多 2 次重试，退避 200ms→800ms，最坏等待约 1.0s）；重试仍失败则该批完整写入**死信文件**（`logs/audit-deadletter.jsonl`）可事后补录，并累计缺失条数 + 节流告警。JSONL 权威记录始终不受影响。生产仍需补**死信自动回灌 + 对账**（见 §7 未覆盖项）。

### 1.2 审计文件改「常驻句柄」（本轮吞吐提升的主因）

**问题**：JSONL 归档在**请求关键路径**上同步写，而旧实现是 `File.AppendAllTextAsync` —— **每条记录都要 open→write→close 一次**。每个聊天请求产生 2~3 条审计记录，于是每个请求要在关键路径上付 2~3 次文件打开/关闭。

**改法**：`AuditLogger` 持有常驻 `FileStream` + `StreamWriter`（`FileShare.ReadWrite`），每条仍 `Flush`（保证记录进入操作系统页缓存、其它进程立即可读，语义与旧实现一致），但不再每次重建句柄。

**实测收益（同一卷、同一条件、3 轮交错）**：

| 配置 | 3 轮实测 QPS | 中位 | 墙钟/请求 | CPU/请求 |
|------|--------------|------|-----------|----------|
| **常驻句柄** | 866 / 989 / 1,025 | **988.8** | 1.19~1.39 ms | 1.0~1.7 ms |
| 逐条 open+close | 292 / 312 / 319 | **312.0** | 3.33~3.66 ms | 1.2~2.0 ms |

⇒ **3.17×**，且 CPU/请求也下降（open/close 在慢速卷上连内核路径解析都在烧 CPU）。

**三个必须知道的代价与配套**：
1. **读者必须用 `FileShare.ReadWrite` 打开**。Windows 上写句柄会挡住用 `FileShare.Read` 打开的读者（`File.ReadAllLines` 正是这个模式）→ 仓库提供 `scripts/read-audit-chain.ps1` 作为合规读取与链式校验示例；
2. **文件在进程运行期间不能被删除或改名**（句柄刻意不给 `Delete` 共享）。否则写句柄会继续写进"已被删除的旧文件"，表面看审计链还在、文件却已消失 —— 那是合规事故而非性能问题。需要轮转请先停服务，或把 `Audit:KeepFileOpen` 置为 `false`；
3. **写失败日志必须节流**。审计写失败在故障期间是**每请求都可能发生**的事件，若逐条打带堆栈的 Critical，宿主会把自己的 CPU 全烧在写日志上：实测出现过 **780 → 38 QPS** ——故障被日志放大成雪崩，比原始故障更严重。现按 30 秒窗口节流并累计上报缺失条数。

### 1.3 审计库与业务库切 SQLite WAL

- `PRAGMA journal_mode=WAL`（读写不互斥）：**库文件的持久属性**，启动时设一次即长期生效；
- `PRAGMA synchronous=NORMAL`（提交免 fsync）：**连接级设置，不是文件属性**。当前只在初始化时的那条连接上执行，写路径的连接由 `IDbContextFactory` 另建，**是否继承取决于连接池是否复用同一条物理连接**（实测复用时会继承，但不保证）。

  ⇒ **"提交不必 fsync" 只能算 best-effort，不能作为稳定结论。** 真正的兜底是批量提交本身 —— 提交次数已被摊薄到原来的 1/200。

  > 2026-10-20 复核更正：早期版本把这两个 pragma 一并说成"库文件持久属性"，是错的。

### 1.4 跨行聚合读路径改走内存快照

跨行卡片查询要同时问 3 家银行。改造前每次请求要开 3 个库、建 3 次连接、发 3 条 SQL，实测比内存字典慢约 5 倍。现在 `BankLedger` 在启动时把本行数据载入内存快照，读路径走内存，**SQLite 仍是持久化的真相来源**。代价：同一库被多个进程打开时快照不共享（Mock Bank 正常单实例运行，不受影响）。

### 1.5 HttpClient 日志降到 Warning

`System.Net.Http.HttpClient` 在 Information 级别下会为**每个 HTTP 请求**打印起止两行，既无诊断价值又让每请求多两次格式化 + 两次控制台写。已按 Microsoft 官方默认做法降为 `Warning`。

### 1.6 顺带修掉的两个真实缺陷

| 缺陷 | 严重度 | 根因 | 修复 |
|------|-------|------|------|
| **MockBank 重启必崩** | **P0** | 「库里是否为空」的种子守卫改读了**内存快照**，而守卫发生在快照载入**之前** → 永远判空 → 每次启动重播种子 → 撞 `accounts.AccountNo` 唯一约束 | 守卫改查数据库（`CountAll` 走 EF 计数） |
| **会话记忆并发下 500** | **P0** | 淘汰逻辑用 LINQ `OrderBy` 排序 `ConcurrentDictionary`，走 `ICollection.CopyTo` 批量拷贝路径 —— 字典被并发修改时抛 `ArgumentException`，随后半填的数组产生 null key，再 `TryRemove` 抛 `ArgumentNullException` | 改用枚举器取快照再排序；并新增 5 项测试（其中 **2 项为并发回归用例**，旧实现下确实失败、修复后通过） |

> 这两个缺陷在低并发下完全看不出来（单元测试、E2E 串行脚本都测不到），
> 是在真实并发压测下才暴露的 —— 第 2 个缺陷在 5 并发下即可复现 HTTP 500。

## 3. 定位过程：怎么找到真正的瓶颈

### 3.1 三层测量，逐层排除

| 层次 | 测什么 | 结论 |
|------|--------|------|
| ① 服务时间 | 1 并发顺序请求的墙钟 | `/api/chat` **2.64ms/请求**；`/health` 0.92ms；MockBank 直连 0.45ms |
| ② CPU 时间 | 宿主进程 `TotalProcessorTime` 增量 | `/api/chat` **1.37~1.48 ms CPU/请求**，12 核机器占用 **4~8%** ⇒ **不是 CPU 瓶颈** |
| ③ I/O 位置 | 把审计文件/库分别挪到本地盘 | **只有审计文件位置有影响**（见 §3.3） |

### 3.2 进程内 A/B：审计落库逐条 vs 批量

`src/StressTest` 新增「测试 7」，在同一个临时 SQLite 库上分别用两种方式写入 300 条审计事件。

| 轮次 | 来源 | 逐条 300 次提交 | 批量 300 条一次提交 | 加速比 |
|------|------|-----------------|---------------------|--------|
| 1 | 本轮 | 1,865.6ms（161 条/秒） | 72.7ms（4,129 条/秒） | **25.7×** |
| 2 | 本轮 | 2,106.3ms（142 条/秒） | 100.4ms（2,989 条/秒） | **21.0×** |
| 3 | 本轮 | 1,288.7ms（233 条/秒） | 72.7ms（4,129 条/秒） | **17.7×** |
| 4 | 复核 agent | 838.5ms（358 条/秒） | 49.2ms（6,092 条/秒） | **17.0×** |
| 5 | 复核 agent | 1,161.7ms（258 条/秒） | 63.8ms（4,704 条/秒） | **18.2×** |
| 6 | 复核 agent | 1,141.8ms（263 条/秒） | 52.5ms（5,709 条/秒） | **21.7×** |
| 7 | 复核 agent | 1,315.8ms（228 条/秒） | 63.3ms（4,739 条/秒） | **20.8×** |

**7 次实测结论：加速比 17.0~25.7×（离散 1.51×），逐条 142~358 条/秒、批量 2,989~6,092 条/秒。**

> ⚠️ **进程内 A/B 本身也有离散度**（约 1.5 倍），结论要看区间不要看单点。
> 绝对速率是**本机**的量级，在别的机器上不复现。

### 3.3 I/O 位置定位：到底是谁在拖后腿

固定 20 并发、4000 请求，只改审计文件与审计库的位置（业务库始终留在 G:，因此 G: 业务 I/O 恒定）。
**下表测于「常驻句柄」改造之前**（即当时的逐条 open+close 实现），正是这组数据把嫌疑指向了审计文件。

| 用例 | 审计文件 | 审计库 | QPS | 墙钟/请求 | CPU/请求 |
|------|---------|--------|-----|-----------|----------|
| A | G: | G: | 473.8 | 2.34 ms | 1.29 ms |
| B | 本地盘 | G: | **982.7** | 1.23 ms | 0.96 ms |
| C | G: | 本地盘 | 472.1 | 2.35 ms | 1.48 ms |
| D | 本地盘 | 本地盘 | 936.3 | 1.25 ms | 1.07 ms |

**结论**：
- **审计库的位置毫无影响**（A 473.8 vs C 472.1）→ 证实批量异步落库已经把它移出关键路径；
- **只有审计文件的位置决定 2 倍吞吐**（A 473.8 vs B 982.7）→ 剩下的每请求磁盘 I/O 就是这个文件；
- 把文件挪到健康本地盘只是缓解，**换成常驻句柄（§1.2）效果更好且不依赖存储位置**（988.8 QPS，同一个 G: 卷）。

复现命令：

```powershell

powershell -NoProfile -ExecutionPolicy Bypass -File scripts\bench-endpoint.ps1 `
    -Url http://localhost:5243/api/chat -Concurrency 20 -Requests 4000 `
    -Method POST -BodyFile <body.json> -Bearer <token>
```

## 4. 测量可靠性（必读）

### 4.1 本机端到端数字不可复现

同一构建、同一套工具、同一天内，对**完全相同**的端点复测：

| 被测对象 | 第 1 次 | 第 2 次 | 离散度 |
|---------|--------|--------|--------|
| `/api/chat` 5 并发 QPS | 290.0 | 142.8 | **2.0×** |
| `/api/chat` 20 并发 QPS | 91.7 | 198.0 | 2.2× |
| `/health` 定点测速 | 1,211 req/s | 282 req/s | **4.3×** |

`/health` 是本项目最简单的端点（无数据库、无审计、无下游调用），它的 4.3 倍离散度说明
**波动来自机器而非应用**。因此：

- ✅ 可以用：进程内 A/B、每请求 CPU 时间、错误率、是否有 5xx、超时数；
- ❌ 不要用：单次端到端 QPS 作为容量结论或 SLA 依据。

### 4.2 三个踩过的测量坑（比结论本身更值得记）

1. **解析千位分隔符**：压测脚本用 `{0:N1}` 格式化，输出是 `1,313.2 req/s`。
   用 `([\d\.]+) req/s` 解析会只取到 `313.2` —— **凭空丢掉千位**，
   一度把「1,043 QPS」读成「43 QPS」，差点把最优点判成最差点。
   ⇒ 解析带千位分隔符的数值前，先去掉逗号。
2. **Windows 命令行传参会吃掉 JSON 里的双引号**：把 `{"a":"b"}` 传给子进程会变成 `{a:b}`，
   服务端直接回 400。`scripts/bench-endpoint.ps1` 因此提供 `-BodyFile` 读 UTF-8 文件传请求体。
3. **不关限流就压测**：限流档位默认开启，429 会让"成功 0/400、吞吐却很高"——
   看起来像性能好，其实是请求根本没进业务逻辑。压测前必须 `RateLimit__Enabled=false`。

### 4.3 复现步骤（必须按顺序）

```powershell
# 1. 先关限流，否则 99% 会被 429 挡掉
$env:RateLimit__Enabled="false"
$env:CoreBank__BaseUrl="http://localhost:5200"

# 2. 起 MockBank（故障注入只在 Development 或 MockBank__EnableFaultInjection=true 下开启）
$env:ASPNETCORE_ENVIRONMENT="Development"
dotnet run --project src/mock-bank/MockBank.Api -c Release -- --urls http://localhost:5200

# 3. 起宿主
dotnet run --project src/src/BankingAgent.Host -c Release -- --urls http://localhost:5243

# 4. 压测（约 2.5 分钟）
dotnet run --project src/LoadTest -c Release -- http://localhost:5243 http://localhost:5200
```

> **两个环境陷阱**（本轮都踩过）：
> 1. `dotnet run` 会自动套用 `Properties/launchSettings.json`（含 `ASPNETCORE_ENVIRONMENT=Development` 与开发密钥），
>    **直接跑 DLL 不会** —— 直接 `dotnet <dll>` 启动会因缺 `Crypto:DataEncryptionKey` 而启动失败，
>    故障注入也会因环境不是 Development 而被静默忽略（返回 200 而不是 503）。
> 2. **E2E 场景 5 会从演示账户转出 30,000 元** —— 但 E2E 现在**自己会重置**：
>    `E2ETest` 的第 0A 步会调用 `POST http://localhost:5200/api/corebank/v1/_admin/reset`
>    把各行数据打回种子态，重置失败即终止 E2E。
>    所以跑 E2E 不需要手工准备数据；**只有压测/负载测试**才需要考虑先重置
>    （它们会消耗演示账户余额；余额被耗尽后 E2E 会以 `INSUFFICIENT_FUNDS` 失败）。

## 6. 容量换算（仅示例，非承诺）

| 指标 | 值 |
|------|-----|
| 峰值吞吐（端到端阶梯，§2） | 198 QPS |
| 峰值吞吐（定点测速，§1.2 改造后） | 约 990 QPS |
| 安全运行水位（198 × 60%） | 119 QPS |
| **安全水位**日处理能力（= 峰值 × 60% × 86400） | 10,264,320 请求/天 |
| **峰值**日处理能力（= 198 × 86400） | 17,107,200 请求/天 |
| 峰值时段承载量（峰值系数 15% 时长 = 12,960s；118.8 QPS × 12,960s） | 1,539,648 请求/天 |

**银行场景估算**（假设 10 万日活用户、人均 10 次对话/日、峰值系数 4）：

```
日请求量 = 100,000 × 10 = 1,000,000
峰值 QPS = 1,000,000 / 86,400 × 4 ≈ 46 QPS
```

> **示例判断（非容量承诺）**：在所有假设成立时，本报告的水位覆盖示例中的 46 QPS；
> 生产副本数必须经目标环境压测、冗余要求和故障场景重新计算。

## 8. 与历史报告的关系

- **历史基线 296 QPS @ 200 并发（P99 812ms，2026-09-28）** 来自**优化前**的架构：
  审计逐条落库、审计文件每条 open+close、Mock Bank 单库 + 全局转账锁。
  旧报告把瓶颈归因为「Mock Bank 的全局锁」，该归因**已随多银行拆分失效**
  （转账锁现在是按行、按账户号的字典序锁）。
- 本报告的 198 QPS 峰值与历史的 296 QPS **不构成直接可比**（架构不同、机器状态不同、噪声量级不同）。
- 真正可比的只有 §3.2 的进程内 A/B、§3.3 的 I/O 位置定位，以及 §1.6 的缺陷清单。
