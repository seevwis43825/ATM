## 1. 测试方法

### 1.1 阶梯加压策略

| 阶段 | 并发数 | 持续时间 | 目的 |
|------|-------|---------|------|
| 预热 | 1 | ~3 秒 | 排除 JIT 编译与连接建立干扰 |
| 1 | 5 | 10s | 低负载基线 |
| 2 | 10 | 15s | 线性增长验证 |
| 3 | 20 | 15s | 拐点探测 |
| 4 | 40 | 20s | 中负载 |
| 5 | 80 | 20s | 高负载 |
| 6 | 120 | 20s | 接近饱和 |
| 7 | 200 | 20s | 饱和探测 |

**停止条件**：错误率 > 5% 或 P95 > 3 秒。

### 1.2 请求构成

交替发送两类只读场景（避免资金操作副作用干扰性能测量）：

- `我有哪些卡` → 卡片管理 Agent
- `我这个月花了多少钱` → 账单分析 Agent

两者都要经过：鉴权 → 限流 → 意图识别 → Agent 路由 → 核心银行 HTTP 调用 → 脱敏返回。

### 1.3 客户端配置

```csharp
MaxConnectionsPerServer = 512
PooledConnectionLifetime = 5 分钟
Timeout = 60 秒
```

| 10 | 4,505 | 100.0% | 300.3 | 31ms | 58ms | 75ms | 175ms |
| 20 | 3,590 | 99.9% | 239.3 | 66ms | 106ms | 132ms | **15,818ms** ⚠️ |
| 40 | 5,901 | 100.0% | 295.1 | 137ms | 183ms | 208ms | 256ms |

**关键观察**：

1. **吞吐在 5 并发就达到 315 QPS**，之后不再增长 —— 说明瓶颈不在 AI Agent，而在**下游 Mock Bank**
2. **并发升高时延迟线性增长**（P50 从 15ms → 699ms），符合排队论预期
3. **20 并发时出现 15.8 秒长尾** —— 这是 SQLite 首次建表 + EF Core 冷启动，非稳态问题
4. **全阶段错误率 < 0.1%**，200 并发下仍零失败

## 3. 瓶颈分析

### 3.1 真实瓶颈：Mock Bank 的全局锁

Mock Bank 的 `TransferService` 用**单个 `SemaphoreSlim`** 保护所有资金变动：

```
所有转账请求 → 竞争同一把锁 → 串行化
```

因此无论 AI Agent 侧并发多高，**核心银行侧始终单线程处理**。这解释了为什么 QPS 在 5 并发就封顶。

**Mock Bank 是模拟系统，真实 CBS 有自己的并发能力**，所以：

> **296 QPS 是本测试环境的天花板，不代表 AI Agent 系统的真实容量。**

### 3.2 AI Agent 侧的实际处理能力

从 5 并发数据反推：P50 仅 15ms，说明**单请求处理耗时约 3ms**（5 并发 ÷ 315 QPS）。

按此推算，若换成无锁的 Mock Bank 或真实 CBS：

| 假设下游能力 | AI Agent 理论吞吐 |
|-------------|-----------------|
| 下游 1000 QPS | 约 900 QPS（Agent 侧成为瓶颈） |
| 下游 3000 QPS | 约 1500 QPS（需加副本） |

### 3.3 单请求耗时拆解

| 阶段 | 耗时估算 | 说明 |
|------|---------|------|
| 鉴权（JWT 验证） | < 0.1ms | 内存 HMAC 计算 |
| 限流检查 | < 0.05ms | 令牌桶，O(1) |
| 意图识别 | < 0.1ms | 当前是关键词匹配；**接 LLM 后会变成 500-2000ms** |
| Agent 路由 | < 0.01ms | 线性扫描 3 个 Agent |
| 核心银行调用 | 2-3ms | HTTP 往返（本地） |
| 脱敏与序列化 | < 0.1ms | 正则替换 |
| **合计** | **约 3ms** | |

> **重要**：当前 `DetectIntent` 是关键词匹配，**没有 LLM 调用**。接入真实 LLM 后，QPS 会下降 100-500 倍（受限于模型推理速度），届时需要**请求合并、语义缓存、异步化**等优化。

## 4. 容量换算

### 4.1 单实例

| 指标 | 值 |
|------|-----|
| 峰值吞吐 | 315 QPS |
| **安全运行水位（60%）** | **189 QPS** |
| 日处理能力 | 16,345,152 请求/天 |
| 峰值日处理（15% 峰值系数） | 2,451,773 请求/天 |

### 4.2 水平扩展

若部署 N 个实例（需先解决会话亲和性）：

| 副本数 | 安全吞吐 | 日处理能力 |
|-------|---------|-----------|
| 1 | 189 QPS | 1,634 万 |
| 3 | 567 QPS | 4,900 万 |
| 5 | 945 QPS | 8,168 万 |
| 10 | 1,890 QPS | 1.63 亿 |

**前提条件**：
- 事件总线必须换成 Kafka（当前内存版不支持多实例）
- 会话状态必须外置（Redis）
- 审计日志必须写共享存储

### 4.3 银行场景估算

假设：10 万日活用户，人均 10 次对话/日，峰值系数 4：

```
日请求量 = 100,000 × 10 = 1,000,000
峰值 QPS = 1,000,000 / 86,400 × 4 ≈ 46 QPS
```

**结论：单实例（189 QPS 安全水位）足够支撑 10 万日活。** 20 万日活需要 2 副本。

## 5. 性能瓶颈清单（生产前必须解决）

| # | 瓶颈 | 当前状态 | 生产要求 | 优先级 |
|---|------|---------|---------|--------|
| 1 | **意图识别无 LLM** | 关键词匹配，0.1ms | 接入 LLM 后 500-2000ms | **P0** |
| 2 | **事件总线内存版** | 单进程 | Kafka，支持多实例 | **P0** |
| 3 | **SQLite 单文件** | 无并发写 | PostgreSQL，读写分离 | **P0** |
| 4 | **无响应缓存** | 每次都调下游 | Redis 缓存 + 语义缓存 | P1 |
| 5 | **DbContext 无池化** | 每次 new | 池化工厂 | P1 |
| 6 | **审计同步写文件** | 阻塞 IO | 异步队列 + 批量落盘 | P1 |
| 7 | **无熔断降级** | 下游挂了会拖垮 | Polly 熔断 + 降级 | **P0** |
| 8 | **轨迹日志无上限** | 内存累积 2000 条 | 落盘 + 环形缓冲 | P1 |
