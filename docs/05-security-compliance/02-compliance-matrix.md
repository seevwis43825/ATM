## 0. 使用口径

> **Current**：本矩阵是“法规义务 → 控制目标”的追踪清单，不是合规认证或已完成声明。源码可验证的主要控制包括 JWT/RBAC、人工确认、速率限制、安全响应头、SQLite 持久化、`TransferRecord` 字段级加密，以及 HMAC 链 JSONL + 独立 `audit_events` 双写。MFA、用户权利完整接口、KMS/TDE/WORM/RLS、监管自动报送和生产监控证据尚未实现。
>
> **Target / Evidence required**：表中 UserConsent、ExplainabilityService、AMLService、PIA、ELK/OSS、自动报送等未能在当前代码中验证的名称均为目标控制点。是否满足具体法律义务必须由法务/合规结合适用主体、部署区域与证据复核。

## 1. 目的

将法律法规的具体义务，**逐条对应**到目标模块、设计决策和控制点上，目标是：

1. 不漏义务：每条法规要求都能在系统设计中找到对应实现
2. 可追溯：任何一项义务 → 设计 → 代码 → 测试 → 审计 都能追溯
3. 可审计：外部审计/监管检查时，能快速提供证据

## 3. 核心义务矩阵

### 3.1 《个人信息保护法》义务矩阵

| 条文 | 义务 | 系统设计 | 控制点 | 验证方式 |
|------|------|---------|--------|---------|
| 第 13 条 | 处理 PII 必须有合法基础（同意/合同/法定义务等） | 用户注册时显式同意（电子协议）；撤回同意通道 | `UserConsent` 聚合根；同意记录表 | 自动化测试；用户功能验证 |

## 5. 合规架构设计（Target；部分已有基础类）

### 5.1 ComplianceGuard（合规拦截器）

作为统一拦截层，所有进入业务核心的请求必须经过：

```
[Request] 
   ↓
[AuthGuard]  ← 身份认证
   ↓
[RateLimitGuard]  ← 限流
   ↓
[ComplianceGuard]  ← 合规拦截
   ├─ ConsentCheck（同意状态）
   ├─ RiskControlCheck（风控规则）
   ├─ AMLCheck（反洗钱）
   ├─ FrequencyLimitCheck（频次限制）
   ├─ HumanInLoopCheck（是否需要人工）
   └─ ContentSafetyCheck（内容安全）
   ↓
[Business Logic]
```

详见 `01-domain/02-domain-model.md` 中 `ComplianceGuard` 设计。

### 5.2 AuditContext（审计上下文）

通过 `IHttpContextAccessor` + `IMessageContext`，每个处理过程都带上：

```
AuditContext {
  UserId, RequestId, TraceId,
  Scenario, Intent,
  ConsentSnapshot（已征得同意列表）,
  RiskScore, AMLFlags,
  Decision, DecisionReason,
  PolicyVersion（合规规则版本）
}
```

### 5.3 ExplainabilityService（可解释性）

`个保法 §24` 要求自动化决策可解释。每次关键决策：

```json
{
  "decision": "REJECTED",
  "scenario": "transfer",
  "reason": "超出单日转账限额",
  "rule_id": "transfer.daily_limit.individual",
  "rule_version": "v1.5",
  "policy_url": "/policy/transfer-limits.html",
  "appeal_channel": "/appeal"
}
```

### 5.4 UserRightsService（用户权利响应）

`个保法 §46-47` 用户权利实现：

| 权利 | 接口 |
|------|------|
| 查询 | `GET /api/v1/users/me/personal-data` |
| 更正 | `PUT /api/v1/users/me/personal-data/{field}` |
| 删除 | `DELETE /api/v1/users/me/personal-data/{field}`（业务受限字段除外） |
| 复制 | `POST /api/v1/users/me/data-export`（异步生成下载包） |
| 撤回同意 | `DELETE /api/v1/users/me/consents/{consent_type}` |
| 投诉 | `POST /api/v1/complaints` |
| 算法说明 | `GET /api/v1/algorithm/explain?scenario=transfer` |

SLA：≤ 30 天（个保法 §47），系统承诺 ≤ 7 个工作日。

## 7. 合规 Review 流程

每个新功能上线前：

1. **业务需求评审** → 合规参与判断是否触发 PIA
2. **设计评审** → 合规对照本矩阵检查
3. **PIA 报告** → 高风险功能必做
4. **上线检查清单** → 含合规项勾选
5. **上线后回顾** → 季度合规 Review

详见 `06-product/02-feature-lifecycle.md`。
