# 抗量子密码学与安全能力评估

> **评估日期**：2026-09-28
> **评估范围**：`src/` 全部代码 + 配置
> **结论提要**：**当前密码学方案不抗量子**，但风险被严重高估了。真正的短板在别处。

---

## 0. 一句话结论

| 问题 | 回答 |
|------|------|
| 密码体系能抗量子破解吗？ | **不能**。HS256 在理论上可被量子算法降级，但实际威胁极低；RSA/ECC 才是真正危险的 |
| 更大的风险在哪？ | 密钥管理、传输加密、速率限制、审计落库——这些**比量子威胁紧迫得多** |
| 现在该做什么？ | 密钥管理 + 传输层加密 + 迁移路径（非量子安全的算法） |

## 1. 抗量子密码学（PQC）现状分析

### 1.1 威胁模型澄清

先区分两类算法，它们的量子风险完全不同：

| 算法类型 | 代表 | 量子攻击 | 实际威胁 |
|---------|------|---------|---------|
| **非对称** | RSA / ECC / ECDSA | **Shor 算法**可完全破解 | 高（需大规模容错量子机） |
| **对称** | AES / HMAC-SHA256 | **Grover 算法**降级一半密钥强度 | 极低 |
| **哈希** | SHA-256 / SHA-512 | 碰撞/原像抗性减半 | 极低 |

**关键认知**：目前不存在能破解 RSA-2048 或 ECC-256 的量子计算机。Google 2024 年 Willow 芯片有 105 量子比特，但**纠错后仅约 1 个逻辑量子比特**——破解 RSA-2048 需要约 4096 个逻辑量子比特。按当前进展，**保守估计还需 10-20 年**。

### 1.2 本系统密码学清单

| 用途 | 算法 | 密钥强度 | 量子风险 | 评估 |
|------|------|---------|---------|------|
| JWT 令牌签名 | **HMAC-SHA256 (HS256)** | 256 bit | Grover 降级至 128 bit | ✅ **实际安全**（128 bit 远超算力极限） |
| 审计链签名 | **HMAC-SHA256** | 256 bit | 同上 | ✅ **实际安全** |
| 审计用户哈希 | **SHA-256** | 256 bit | 原像抗性降至 128 bit | ✅ **实际安全** |
| 会话幂等键 | **SHA-256** | 256 bit | 同上 | ✅ **实际安全** |
| 数据传输 | **无 TLS** | — | — | ❌ **完全缺失** |
| 数据库存储 | **无加密** | — | — | ❌ **完全缺失** |
| 数据库账号密码 | **明文配置** | — | — | ❌ **完全缺失** |

**诚实结论**：本系统**只用了对称密码**（HMAC-SHA256），**没有用任何非对称密码**。因此：

> **当前不存在「被量子破解」的实际风险**，因为对称密码在量子时代仍保有 128 bit 有效强度。

但这是**侥幸而非设计**。真正的抗量子方案要求：

1. **密钥交换**必须从 RSA/ECC 迁移到 ML-KEM（Kyber）/ ML-DSA（Dilithium）——**本系统完全没用非对称，所以也没有这个问题**
2. **签名算法**若未来引入 ECDSA，需迁移到 ML-DSA
3. **对称密钥长度翻倍**：若考虑长期保密（>20 年）数据，HMAC-SHA256 应升级为 HMAC-SHA512

### 1.3 NIST 后量子标准状态（2024-2026）

| 标准 | 算法 | 用途 | 状态 |
|------|------|------|------|
| FIPS 203 | **ML-KEM**（原 CRYSTALS-Kyber） | 密钥封装 | ✅ 2024-08 正式发布 |
| FIPS 204 | **ML-DSA**（原 CRYSTALS-Dilithium） | 数字签名 | ✅ 2024-08 正式发布 |
| FIPS 205 | **SLH-DSA**（原 SPHINCS+） | 哈希签名 | ✅ 2024-08 正式发布 |

**重要**：中国商用密码标准（SM2/SM3/SM4）中，**SM2（非对称）不抗量子**；**SM3（哈希）抗量子强度减半**；**SM4（对称）需用 SM4-GCM 且密钥翻倍**。若银行系统使用国密算法，需关注同样问题。

### 1.4 建议的密码演进路径

```
当前 (2026)                    过渡期 (2028-2032)              目标 (2032+)
─────────────────────────────    ──────────────────────────      ──────────────────────────
HS256 JWT ✅                    HS512 JWT（密钥翻倍）           ML-DSA 签名的 JWT
HMAC-SHA256 审计 ✅             HMAC-SHA512 审计                HMAC-SHA512 审计（保持）
TLS 1.3 + ECDHE ❌              TLS 1.3 + X25519MLKEM768        TLS 1.3 + ML-KEM-768
AES-256-GCM 存储 ❌             AES-256-GCM 存储                AES-256-GCM（保持）
```

**注意**：`.NET 10` 已内置 `ML-KEM` 支持（`System.Security.Cryptography.MLKem`），迁移成本不高。

## 2. 真正的安全短板（比量子威胁紧迫得多）

### 2.1 密钥管理（最严重）

| 问题 | 风险等级 | 现状 | 立即行动 |
|------|---------|------|---------|
| **签名密钥硬编码在配置** | 🔴 极高 | `Jwt:SigningKey` 在 `appsettings.json` | 改用环境变量 + KMS |
| **密钥无轮换机制** | 🔴 高 | 密钥固定不变 | 实现双密钥轮换（当前+上一个） |
| **密钥无版本标识** | 🟡 中 | 无法追踪哪把密钥签的 | 令牌加 `kid` 头部 |
| **无密钥吊销** | 🔴 高 | 泄露后无法作废 | 引入密钥版本黑名单 |
| **开发密钥告警仅日志** | 🟡 中 | 启动时 Warning | 改为生产环境直接启动失败 |

**代码位置**：`src/BankingAgent.Base/Security/Auth/TokenService.cs:26-38`

### 2.2 传输安全

| 问题 | 风险等级 | 说明 |
|------|---------|------|
| **无 TLS** | 🔴 极高 | JWT 令牌明文传输，可被嗅探 |
| **无 mTLS** | 🔴 高 | 服务间调用无身份验证 |
| **无证书固定** | 🟡 中 | 无法防中间人 |

**当前测试全部走 HTTP**（`http://localhost:5243`），生产必须强制 HTTPS。

### 2.3 数据静态加密

| 问题 | 风险等级 | 说明 |
|------|---------|------|
| **数据库未加密** | 🔴 高 | 拖库即明文 |
| **敏感字段未加密** | 🔴 高 | 身份证、银行卡号明文存储 |
| **未接 KMS** | 🔴 高 | 无密钥托管 |
| **备份未加密** | 🟡 中 | 备份文件可读 |

**数据分级**已实现（L1-L4），但**脱敏 ≠ 加密**。生产需要：
- 数据库层 TDE（透明数据加密）
- 敏感字段应用层加密（身份证、卡号）
- 密钥托管在 KMS / HashiCorp Vault

### 2.4 抗入侵能力

| 攻击面 | 当前防护 | 缺口 |
|--------|---------|------|
| **SQL 注入** | ✅ EF Core 参数化 | 无 |
| **越权访问** | ✅ JWT + 令牌身份绑定 | 无 |
| **暴力破解** | ❌ **无速率限制** | 登录接口可被爆破 |
| **令牌窃取** | 🟡 30 分钟过期 | 无刷新令牌吊销机制 |
| **中间人** | ❌ 无 TLS | 生产致命 |
| **XSS** | ❌ 无输出编码 | 前端未实现 |
| **CSRF** | ⚠️ Bearer 天然免疫 | 无 Cookie |
| **插件投毒** | 🟡 依赖拓扑校验 | **无插件签名验证** |
| **供应链攻击** | 🟡 仅有目录扫描 | 无 DLL 签名校验 |
| **DDoS** | ❌ **无限流** | 易被刷 |
| **日志注入** | ✅ JSON 序列化 | 无 |
| **反序列化** | ✅ System.Text.Json | 无 |

**最危险的两项**：
1. **无限流** —— 任何人都可以无限调接口，耗尽资源 + 暴力破解令牌
2. **无插件签名** —— 任何人只要能写入 `plugins/` 目录就能替换业务逻辑

## 5. 密码敏捷性（Crypto-Agility）设计建议

**目标**：算法可替换而不改动业务代码。

```json
{
  "Crypto": {
    "JwtSigningAlgorithm": "HS256",
    "AllowedAlgorithms": ["HS256", "HS512", "PS256", "EdDSA"],
    "KeyRotationDays": 90,
    "KeyProvider": "Environment",           // Environment | Vault | AwsKms
    "Encryption": {
      "Algorithm": "AES-256-GCM",
      "KeyProvider": "Vault"
    },
    "PostQuantum": {
      "Enabled": false,                      // 未来开启
      "KexAlgorithm": "X25519MLKEM768",
      "SignatureAlgorithm": "ML-DSA-65"
    }
  }
}
```

**关键**：`AllowedAlgorithms` 列表让算法升级只需改配置；`KeyProvider` 抽象让密钥存储可替换。
