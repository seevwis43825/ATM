# 发布流程（Release Process）

> **状态**：评审中 · **所有者**：产品 · **版本**：v1.0
> **最后更新**：2026-09-21

---

## 1. 目的

建立可重复、低风险、可回滚的发布流程：

1. **零停机**：发布期间用户无感知
2. **可灰度**：异常时影响范围可控
3. **可回滚**：30 秒内回滚到上一版本
4. **可审计**：每次发布都有记录

---

## 2. 发布节奏

| 类型 | 频率 | 时间 | 说明 |
|------|------|------|------|
| **常规发布** | 每周二/四 | 上午 10:00 | 累计 1 周的 Feature |
| **紧急修复** | 随时 | 任意 | 仅限 P0 bug、安全补丁 |
| **合规/法规相关** | 按需 | 任意 | 算法备案、数据合规 |
| **重大版本（v 主版本升级）** | 季度 | 月初 | 提前 1 周通告 |

> **不推荐**：周五发布（周末无人响应）、节假日发布、凌晨发布（除非灰度发布）。

---

## 3. 发布前（Pre-Release）

### 3.1 发布前 3 天（周二/周五发布前的周五）

- [ ] **冻结代码**：下一个发布日不再合入新 Feature（仅 Bug Fix）
- [ ] **Release Candidate（RC）**：主干创建 RC 分支
- [ ] **集成测试**：完整测试套件执行
- [ ] **性能测试**：预发环境跑性能基线
- [ ] **安全扫描**：SAST / 镜像扫描 / 密钥扫描

### 3.2 发布前 1 天

- [ ] **预发部署**：RC 分支部署到预发环境
- [ ] **预发验证**：QA 完整回归
- [ ] **业务验证**：产品 + 业务 owner 在预发环境跑通核心场景
- [ ] **回滚演练**：确认上一版本镜像可用 + 回滚脚本就绪

### 3.3 发布日当天（T-2 小时）

- [ ] **最终检查**：CI 全绿，无 P0/P1 遗留
- [ ] **生产部署窗口确认**（无人值守时段避免）
- [ ] **On-call 确认**：发布期间至少有 1 名资深工程师在场
- [ ] **回滚方案确认**：FeatureFlag 关闭、回滚脚本、上一版本镜像
- [ ] **通讯准备**：Release Notes、客服话术（如有用户侧变化）
- [ ] **监控准备**：Grafana 大盘打开、关键告警设为静音取消

---

## 4. 发布中（Release）

### 4.1 发布步骤

```
1. 蓝绿部署：先部署新版本到 "绿" 环境
2. 内部冒烟：新版本上 5% 流量（仅团队 + 种子用户）
3. 健康检查：等待 5 分钟，观察关键指标
4. 灰度扩展：10% → 25% → 50% → 100%
5. 旧版本保活：旧版本保留 ≥ 24 小时（便于回滚）
6. 资源回收：24 小时后回收旧版本资源
```

### 4.2 灰度发布（Canary）

使用 K8s + Argo Rollouts（或自研脚本）：

```yaml
# rollout.yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: agent-core
spec:
  replicas: 6
  strategy:
    canary:
      steps:
        - setWeight: 5        # 5%
        - pause: { duration: 5m }
        - setWeight: 25       # 25%
        - pause: { duration: 10m }
        - setWeight: 50
        - pause: { duration: 10m }
        - setWeight: 100
      analysis:
        templates:
          - templateName: success-rate
        args:
          - name: service-name
            value: agent-core
```

### 4.3 关键监控指标（灰度期间盯）

| 指标 | 通过条件 |
|------|---------|
| **错误率** | 新版本错误率 ≤ 旧版本 + 1% |
| **P99 延迟** | 新版本 P99 ≤ 旧版本 + 20% |
| **CPU/Memory** | 无明显上涨（< 30%） |
| **核心业务 KPI** | 转化率 / 成功率无显著下降 |

### 4.4 异常处理

任一指标恶化：

| 异常 | 动作 |
|------|------|
| 错误率 +0.5% | 暂停灰度、观察 5 分钟 |
| 错误率 +1% 或 P99 +50% | 立即回滚（`kubectl rollout undo`）|
| 涉及资金风险 | 立刻回滚 + 通知架构师 |
| 用户投诉突增 | 暂停灰度 + 调查 |

## 5. 发布后（Post-Release）

### 5.1 发布后 1 小时

- [ ] **全量确认**：100% 流量已切到新版本
- [ ] **核心场景验证**：抽样 10 笔关键业务（转账、对话）
- [ ] **数据一致性核对**（如涉及 DB 迁移）
- [ ] **监控无异常**

### 5.2 发布后 24 小时

- [ ] **业务指标对比**：与上一版本对比关键指标
- [ ] **用户反馈汇总**：客服 / 微博 / 应用商店评价
- [ ] **性能基线更新**：记录新版本基线
- [ ] **资源回收**：24h 后清理旧版本

### 5.3 发布后 72 小时

- [ ] **完整复盘**：在迭代复盘会上回顾本次发布
- [ ] **遗留问题**：列出后续跟踪项

## 6. 紧急发布（Hotfix）

### 6.1 适用场景

- P0 bug（如转账金额计算错误）
- 安全漏洞（如数据泄露）
- 合规问题（如审核未通过必须立刻修复）

### 6.2 流程（简化）

```
1. 创建 hotfix 分支（从主干拉）
2. 最小修复 + 测试
3. 跳过 RC：直接合并到主干
5. 部署：预发 → 生产（紧急灰度 5% → 50% → 100%）
6. 监控 + 通报
7. 48h 内补 RC + 正常发布流程
```

### 6.3 Hotfix 通讯模板

> **【紧急发布】AI Banking Agent v0.4.1-hotfix.1**
>
> - 时间：YYYY-MM-DD HH:MM
> - 修复：<简述>
> - 影响：<无 / 部分用户>
> - 发布人：张三
> - 已通知：客服 / 运营

## 7. 回滚（Rollback）

### 7.1 触发条件

- 错误率持续超阈值
- 业务关键指标恶化
- 安全告警
- 用户投诉爆发
- 架构师判断需要回滚

### 7.2 回滚策略（由快到慢）

| 策略 | 响应时间 | 适用 |
|------|---------|------|
| **FeatureFlag 关闭** | ≤ 10s | 新功能异常 |
| **流量切回旧版本** | ≤ 30s | K8s 蓝绿切回 |
| **kubectl rollout undo** | ≤ 1min | 版本回退 |
| **数据库回滚（DROP/COLUMN 加回）** | ≤ 5min | 涉及 schema |
| **完整重建（数据库 + 应用）** | ≤ 30min | 灾难场景 |

### 7.3 回滚流程

```
1. IC 决策回滚（事故频道内）
2. 执行回滚命令（一人执行，一人核对）
3. 等待 1 分钟，观察恢复
4. 通知相关方（用户/客服，如影响）
5. 保留旧版本 ≥ 24h
6. 48h 内写 Postmortem（参见 04-operations/03-incident-response.md）
```

## 8. 数据库变更（Migration）

### 8.1 原则

- **向后兼容**：新代码必须兼容旧 schema
- **小步快走**：避免单次大改
- **可回滚**：每个 Migration 都有 Down

### 8.2 三阶段发布（如有破坏性变更）

```
阶段 1：双写
   - 应用代码同时写旧列 + 新列
   - 读仍读旧列

阶段 2：迁移
   - 后台 job 把旧列数据迁移到新列
   - 读切到新列
   - 旧列保留（不删除）

阶段 3：清理
   - 确认无读旧列后，删除旧列
   - 通常在下个大版本清理
```

### 8.3 工具

- **EF Core Migrations**（推荐）
- **Flyway**（备选）

> 发布人：张三

## 🎉 新功能

- <功能 2>

## 🐛 Bug Fix
- <修复 1>

## ⚡ 性能优化
- <优化 1>

## ⚠️ 重大变更（Breaking Change）
- <变更说明 + 迁移步骤>
